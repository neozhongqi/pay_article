# 支付智能体的技术实现与商业落地

> 主题编号：S-04  
> 匹配热点：万事达卡帅意华提出智能体商务五大支付挑战、Agent Pay for Machines 开放早期接入、国内 A2P2 / Token Pay / AI 专属卡并行落地  
> 成稿日期：2026-10-21  
> 目标读者：支付技术研发人员、智能体平台与收单产品经理、持牌支付机构跨境与创新业务负责人

---

## 一、今天的问题，已经从「授权怎么写」变成「系统怎么跑起来」

2026年10月21日，移动支付网发出一篇并不长的现场综述：万事达卡大中华区产品与解决方案副总经理帅意华，在10月15日的跨境数字金融大会上，把智能体商务的支付难题收成五条——身份识别、交易安全、意图与授权验证、协议编排、积分与忠诚度。同一周，万事达卡又在 Cloudflare Connect 上把 Agent Pay for Machines 从新闻稿推进到可演示、可申请早期接入的状态：一个营销智能体领到任务和预算，先后向两家独立商户完成九笔支付，全程没有新开账户、没有逐家签账单。

这两条信息叠在一起，正好对应记忆主题库 S-04：支付智能体的技术实现与商业落地。它同时咬合 H-04（AI Agent 从工具变成管家）、H-05（万事达卡的代理支付棋局）和 H-01（AI 钱包）。10月19日成稿已经回答过 S-01 的问题——用户的支付授权如何保障。今天更值得写的，不是再复述一遍「必须本人确认」，而是：**授权协议写完之后，技术栈怎么接、商业模式怎么活、商户为什么愿意接。**

帅意华把智能体商务放进 3.0 阶段：1.0 是线下门店，2.0 是线上电商，3.0 是智能体代表消费者以数字方式完成交易。演进路径也很清楚：先做单一商户购买，再做多商户协调，最后做到条件触发的延迟购买。行业演示已经能「说一句话就下单」，卡住规模化的却是另外一件事——现有支付基础设施是为人设计的，智能体却要在机器速度上被识别、被授权、被结算、被追责。

万事达卡自己把这句话说得更硬：支付不是最难的部分，权限才是。难的是让正确的智能体，带着正确的权限，完成正确的一笔交易。S-04 要回答的，就是这套「正确」如何被工程化和产品化。

## 二、五个挑战不是清单，是一条必须按序打通的技术链

把帅意华的五条挑战摊开，会发现它们不是并列的公关话术，而是一条从身份到商业的实现链路。任何一环断掉，后面的「自动下单」都只是演示。

### 1. 身份：先回答「谁在花这笔钱」

当下智能体缺少统一身份，商户很难验证它有没有权限、值不值得授信。传统支付里，身份几乎等于「人 + 设备 + 账户」。智能体进来之后，至少要同时绑住四件事：出资的真实用户或企业、被授权的智能体版本、运行时环境是否可信、此次任务对应哪一张委托凭证。

京东 6 月发布的 A2P2 协议，把这件事做成了 ARI（智能体运行时身份）：扣款瞬间要同时核验资金由本人承担、执行的是用户唯一授权的智能体版本、运行环境未被注入。万事达卡 Agent Pay 一侧则强调认证凭证和「可认证意图」（Verifiable Intent），让智能体在不同生态里能被识别，而不是每次都靠商户自己猜。中国支付清算协会《智能体支付应用自律公约》要求会员单位在 KYC 之外探索 KYA（了解你的智能体），说的是同一层。

没有这一层，后面所有风控都是在给匿名脚本做授信。

### 2. 凭证与交易安全：机器交易不能沿用人类页面的安全假设

智能体、商户和支付服务商处理凭证的方式各异，直接后果是支付失败、安全性不足、风险决策不一致。人类结账页上的 Cookie、验证码、短信和确认按钮，对 Bot 来说既是障碍，也是攻击面。智能体商务需要的是机器可读的支付请求：金额、币种、收款方、用途、有效期，一次签名，多方核验。

10月20日的演示把这条路径写得很具体。服务端返回 HTTP 402 Payment Required，智能体在预算内签发支付凭证，商户核验后交付服务，凭证可离线聚合、事后赎回。AWS Bedrock AgentCore、Anchor Browser、Solana 上的 x402 批量结算，走的都是「先授权额度、再按签名消费、最后一次性清算」的路子。它解决的是高频、小额、跨服务的连续支付，而不是再给每个 API 开一张预付费账号。

对持牌机构，这意味着风控要从「拦 Bot」改成「识别受信智能体」。旧规则会把正常的机器支付当成攻击；新规则如果只放行、不核验凭证，又会把提示词注入和越权调用放进来。

### 3. 意图与授权：自然语言必须被编译成可执行的权限对象

当意图与授权隐含或不一致时，商户和发卡机构无法核实授权内容，争议也无从裁决。这是 S-01 已经展开过的核心，但落到 S-04 的实现层，关键不再是原则，而是编译器。

用户说「帮我看看附近团购」和「帮我把这家套餐买了」，语义很近，资金后果完全不同。A2P2 的做法是把自然语言变成「任务委托凭证」，扣款前实时核对金额、品类、收款方是否仍在授权范围内。微信支付的 AI 专属卡把智能体可用资金从主账户拆出去，余额用户自定，资金变动仍需本人确认。支付宝则把能力拆成 Token Pay、Agent Pay、Vibe Pay、Skill Pay、Machine Pay，不同对象用不同授权粒度。万事达卡的公式更工程化：授权一次，交易多次；先保证支付，后完成结算。

实现上至少要有四类对象：任务边界、资金载体、单笔校验、撤销与回退。缺任何一类，授权协议都会停在 PDF 里。

### 4. 协议编排：商户不可能为每个智能体平台单独接一次

每个 AI 智能体平台都有自己的协议，商户逐一集成，成本和复杂度会按平台数线性上升。这是商业落地里最容易被产品发布会跳过、却最先劝退中小商户的一条。

2026 年已经能看到多套并行标准：京东 A2P2、银联智能体支付开放协议框架、支付宝 Agent 支付、Visa Intelligent Commerce / Trusted Agent Protocol、万事达卡 Agent Pay 与 Agent Pay for Machines、OpenAI 与 Stripe 的 ACP、谷歌 UCP，以及开放的 x402。对商户来说，标准变多并不等于互联互通，反而可能是新一轮烟囱。

商业上真正能落地的编排，不是再发明一个协议，而是让收单、钱包、智能体平台和卡网络共用一层最小信任对象：身份、权限、凭证、争议。帅意华提醒的「复用现有支付基础设施」，指的就是这件事——智能体支付要长在清算、风控和商户管理体系上，而不是另起一套无法对账的平行宇宙。

### 5. 忠诚度与商业模式：智能体如果只比价，商家会失去接它的理由

智能体驱动的购买优先考虑价格、速度与货源，忠诚度手段被边缘化，复购价值被削弱。这看起来像营销问题，其实是商业落地的总开关。如果智能体只会给用户挑最便宜的那一家，商户接入智能体支付的动力就会迅速下降；平台也会发现，自己过去靠会员、积分和品牌心智积累的护城河，在 Agent 决策里突然失效。

蚂蚁在生态大会上把变化说成「从商品交易变成任务交易」「从人找服务变成服务找人」。对商户，这意味着经营单元要从 SKU 升级到 solution：不是只卖一张电影票，而是承接「下午两点看电影并顺路买杯冰美式」整段任务。对支付机构，积分、券、权益必须变成智能体可读、可比、可核销的支付能力，而不是藏在人类 App 里的彩蛋。谁先把忠诚度编译进决策，谁才有机会在比价之外留下自己。

## 三、商业落地已经分出三条轨道，不能再用一个「AI 支付」来概括

把 2026 年 6 月到 10 月的产品放在一张图上，支付智能体其实走了三条轨道。S-04 的「落地」，要按轨道验收，而不是按发布会次数验收。

### 轨道一：C 端代客下单，先把钱从主账户里拆出来

微信 AI 专属卡、支付宝「阿宝」和 AI 付、京东 AI 付，走的是这一条。用户能理解的体验是：智能体可以去办事，但预算、场景和最终拍板权仍在自己手里。它解决的是「不敢开」——主账户不被直接调用，越权想象被压住。

这条轨道的技术门槛不在模型，而在资金隔离、笔笔确认、账单可回看。它的商业天花板也很清楚：如果每一笔都要人点，智能体就还是「会说话的收银台」。协会把阶段分成辅助支付、预设条件自主支付、泛条件自主支付，后两阶段须报备并做安全评估。C 端现在大多停在第一阶段，这是对的；但产品如果永远不敢进入「预设条件」，就谈不上智能体，只谈得上对话式导购。

### 轨道二：企业与开发者侧的 Token / API / 机器支付

支付宝 Token Pay 面向大模型订阅、席位分发和按量计费；万事达卡 Agent Pay for Machines 面向数据、算力、API、模型调用等数字服务；汇丰与蚂蚁数科在代币化存款测试网上验证过 AI 代理支付的实时结算。这条轨道的用户不是「帮我买杯咖啡」的个人，而是要让软件在预算内连续采购数字生产资料的企业。

它的商业模式更接近新基建：一次授权、多次交易、凭证聚合、多轨结算（卡、账户、稳定币）。Cloudflare Connect 的演示已经把最小闭环跑通——任务、预算、402、签名凭证、两家商户、九笔支付、法币或稳定币结算。早期接入开放的是买家侧和卖家侧 API、工具包和沙箱。对研发团队，这比再看一遍「说句话就能付」更接近可开工的规格。

### 轨道三：跨境与卡组织互联，把智能体接进已有网络

京东与万事达卡的代理支付布局、蚂蚁国际与 Visa / Mastercard 的 KYA 协同、银联开放协议强调的跨机构跨场景互联，走的是这一条。跨境智能体支付会同时碰到身份互认、制裁名单、汇率、争议处理和本地支付方式。帅意华的分享主题本身就叫「跨境智能体支付机遇与挑战」，说明卡组织并不把智能体支付看成又一个国内 C 端入口，而看成现有全球收单网络的新交易主体。

这条轨道决定中小支付机构能不能跟上。自己再写一套 Agent 协议意义有限；能做的是按开放协议完成准入，把商户、KYC、KYA、交易监测接上，让智能体订单能进现有对账和清算。统一接口来了，主体责任不会变少。

## 四、技术实现的验收标准：七个对象，缺一就还是演示

把三条轨道折回工程，支付智能体要落地，至少要交出七个可测试对象。

1. **智能体身份。** 含开发者、版本哈希、运行时环境、所属用户或企业。不能只有一个 API Key。  
2. **任务委托凭证。** 自然语言必须编译成金额上限、品类、收款方、有效期、可否拆单。  
3. **资金载体。** 专用卡、专用户、Token 额度或企业预算池，与主账户隔离。  
4. **机器可读的支付请求。** 用 402 / 开放协议，而不是让智能体去点人类页面。  
5. **实时裁决。** 单笔核对凭证、身份、限额、名单和商户风险，给出放行、补确认或拒绝。  
6. **存证链。** 用户授权、模型决策、支付指令、风控结果、交付回执绑在同一事实锚点上。  
7. **争议与回退。** 买错、幻觉、注入、商户未履约时，能定位责任并原路退回，而不是只剩客服话术。

这七个对象对得上，才谈得上「技术实现」。对不上，对外可以叫 AI 钱包，对内仍是套了大模型的收银台。

## 五、给两类读者的落地清单

### 对技术研发与架构

1. 先做身份和凭证，再做自动扣款。没有 KYA 和任务凭证，自主支付只是把风险前移到模型输出。  
2. 把「人确认」做成可配置策略，而不是写死在主流程里。C 端默认确认，企业侧按金额、品类、新商户分级；否则永远无法从辅助支付进入预设条件支付。  
3. 不要让智能体去操作网页结账。优先接开放协议和结构化支付请求，页面自动化只作为兼容层，并单独加风控。  
4. 风控规则按交易主体分叉：对人沿用设备、行为、验证码；对智能体核验版本、运行时、委托凭证和预算消耗曲线。  
5. 协议适配做成适配器，而不是为 A2P2、x402、银联框架、卡组织接口各建一套账务。账务对象必须统一。  
6. 把积分、券、权益变成智能体可询价、可核销的支付工具，否则商户侧的忠诚度会在比价里蒸发。  
7. 存证从第一笔试点就做。出了错还要靠聊天记录举证，商业上走不远，监管上也过不了报备。

### 对产品、商户与持牌机构业务侧

1. 先选轨道，再写 PRD。代客下单、Token / API 采购、跨境收单，不是同一个产品，不要用一个「AI 支付」看板混着管。  
2. 给商户算清楚「接智能体」的理由。除了多一个入口，还要能带来任务级订单、可预期结算和可解释争议；否则商户没有理由为第五个协议再接一次。  
3. 把费率、结算、对账和退款规则写成智能体也能读的商户画像。智能体不会看招商手册。  
4. 忠诚度要进决策，而不是事后发券。会员价、积分抵扣、品牌约束应成为授权边界的一部分。  
5. 跨境场景单独做可收性评估。智能体下了单，钱过不了境、换不了汇、对不上贸易背景，就是把 S-03 的汇困问题自动化了。  
6. 对外宣传区分「演示可用」和「可商用」。沙箱九笔支付证明闭环存在，不证明备付金、反洗钱、客诉和差错处理已经就绪。  
7. 守住持牌主体责任。智能体平台可以做意图理解和任务编排，账户、清算、备付金和用户资金安全仍在持牌机构。

## 六、结论：落地不看会不会说话，看七个对象能不能对上账

回顾 10 月 21 日这一轮热点，帅意华的五条挑战、万事达卡的早期接入、国内已经铺开的 AI 专属卡、Token Pay 和 A2P2，说的不是又一次「AI 能替你付钱」，而是支付智能体终于从授权叙事走进实现叙事。

S-01 解决的是「谁有权花」。S-04 要解决的是「权拿出来之后，系统怎样连续、安全、可对账地花出去，并且让商户愿意收款」。身份、凭证、意图编译、协议编排、忠诚度重写，五件事必须按序打通。少做身份，商户不敢信；少做凭证，风控只能一刀切；少做编排，中小商户进不来；少做忠诚度，商户不肯来。

因此，判断一个支付智能体产品是不是真落地，标准可以收成四句：

- 智能体有没有独立于主账户的身份和资金载体；  
- 自然语言有没有被编译成可校验的任务凭证；  
- 商户能不能一次接入、对上现有清算和对账；  
- 出错之后，找得到持牌主体、找得到存证，而不是只找得到一句「模型理解偏差」。

四句里有一句含糊，就还是演示。四句都清楚，商业才开始。
